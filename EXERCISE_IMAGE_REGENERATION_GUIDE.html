Exercise Image Regeneration Guide

Every one of the 87 files in photos/exercises/ carries instructional text burned into the pixels. Some of it is English, some of it is Turkish, and no translation layer can reach any of it — a Turkish reader meets English on some exercises and an English reader meets Turkish on others. This document is the brief for replacing all 87.

What is actually wrong with these files

They are not photographs with a caption. They are infographics. The audit found four distinct layouts:

layoutcountwhat the pixels carry
Two-panel before/after
800×437		37 A caption bar top and bottom. Sometimes English over Turkish, sometimes the same English twice.
Step filmstrip
800×533		48 A title, 3–6 numbered steps each with a Turkish instruction paragraph, per-frame time chips, and a TOPLAM SÜRE timeline. The isometric holds in this size class use a variant with one large photo and a Turkish sidebar — starting position, movement, breathing, cues, target muscles — instead of the panel strip.

Read this before generating anything

The text in these files is not decoration — on the filmstrip layouts it is the coaching content: the steps, the tempo, the breathing cues, the muscles worked. Generating a clean photograph deletes it.

That is still the right move, because content burned into a pixel cannot be translated, corrected, resized, read aloud by a screen reader, or shown at a larger text scale. But the replacement is only complete when that content lands somewhere the app can render it — the description and short_tip columns the exercise catalogue already has, or new step rows beside them. The images and the step copy are one project, not two.

Why every prompt says "centred, generous margin"

ExerciseGuidePlayer renders these with BoxFit.cover inside a picture-in-picture slot and applies a slow Ken Burns pan-zoom. The frame is therefore cropped, and the crop moves. Anything near an edge is not reliably on screen — which is also why a burned-in caption bar is doubly wrong here: the pan can slice it in half.

Drop-in contract

Keep the filename and the folder and there is no code change at all. ExerciseMediaRegistry.localImagePath() derives the path from the slug — photos/exercises/<PascalCase>.webp — and photos/exercises/ is already declared in pubspec.yaml. Aspect ratio is free: cover crops to the slot, so the 3:2 in these prompts changes nothing structurally.

Export as WebP. The current 87 total 2.7 MB, and holding roughly that budget keeps the APK where it is.

Which categories need motion, and which do not

The founder asked where a looping demonstration is required and where a still is enough. The dividing line is not the muscle group — it is whether one frame can show what the exercise is.

classcountverdict
Isometric holds
plank, dead hang, child's pose, stretches		 9 A still is not a compromise, it is the exercise. There is nothing to animate. Never spend a video budget here.
Single-plane strength
presses, rows, curls, squats, hinges		 59 A still at the hardest position is sufficient, and is arguably better than a loop: the position that gets corrected is the one the user has to be shown, and a loop shows it for a fraction of a second.
Ballistic, locomotive and multi-position movements
burpees, swings, jumps, crawls, carries, shuffles, cleans, thrusters, wall walks		 19 These genuinely require a loop. A still of a kettlebell swing and a still of a front raise are the same photograph. The information is the path, and a frame cannot carry a path. This is also exactly the set the current filmstrip layout was invented to fake.

Each card below is tagged with its class, and the toolbar filters on it. If the budget only covers part of the library, the 19 tagged needs motion are where a loop buys something a still cannot.

Recommended media strategy

  1. Two tiers, not one. A bundled WebP still for every exercise — it is the offline floor, it is what renders on a cold start, and it is what the user sees when the network is gone. A hosted loop on top for the 19 that need one. Never ship a movement with only a loop.
  2. The loop is hosted, and today it has to be. ExerciseGuidePlayer passes only http paths to the video controller and deliberately drops bundled asset paths to the fallback tile — a branch added because malformed-URL inputs were crashing. So a looping demo means a Supabase-hosted file plus the existing file-cache warm, not a new asset in the APK. Good outcome anyway: 19 loops in the binary would cost more than the entire current image library.
  3. Make the registry manifest-driven. ExerciseMediaRegistry still needs a hand edit to _localImageSlugs for every file added. WorkoutBackgroundRegistry beside it already resolves from the asset manifest, so dropping a correctly-named file in is the whole procedure. Porting that pattern removes the one step in this pipeline a person can forget.
  4. Silent, muted, 3–5 s, no audio track. These play in a picture-in-picture slot beside a live workout. An audio track would fight the voice coach and is dead weight in the file.
  5. The step copy goes to the database, not the pixels. Whatever the filmstrips were saying belongs in the exercise catalogue next to description and short_tip, where it is translatable, screen-reader reachable and scalable with the user's text size. That is also what makes the next language a content task rather than 87 more renders.

Production pipeline

  1. Generate at 1536×1024 or larger from the prompt on the card.
  2. Reject any render with a letter or a digit in it. Image models put text on gym walls, plates and clothing unprompted. This is the one check that cannot be skipped, because it is the entire reason the library is being replaced.
  3. Check the pose is the one named in the prompt. A model will happily return a plausible athlete in the wrong position, and a wrong instructional image is worse than none.
  4. Crop to 3:2, centred on the athlete, and confirm nothing important sits within ~8 % of any edge — that band is what the pan-zoom eats.
  5. Export WebP, quality ~82, target < 40 KB.
  6. Save over the existing file at the exact path on the card. No code change, no registry edit, no pubspec edit.
  7. Re-run flutter build apk --release and confirm the size has not moved materially.
